# Modbus_RS485_PC

## STM32 Modbus RTU 采集路由从机

运行在 **STM32F103C8T6** 上的裸机 Modbus RTU 路由固件。PC 主站的请求从 USART1 进入，固件先完成帧长和 CRC 校验，再按从机地址分流：

- `0x01`：转发到 RS485 总线，由外部温湿度变送器自行应答，应答原样回传 PC。
- `0x02`：本机 DHT11 虚拟从机，使用 `0x03` 返回温度、湿度保持寄存器。
- 其他地址：静默丢弃并增加诊断计数。

当前分支为 **`modbus_congji`**，包含 M0–M3 分层、双地址路由和本机 DHT11 从机。默认分支 `main` 仍是 v1.0.0 双向透传桥，本分支尚未合并到 `main`。

> 本仓库负责“从机侧采集与路由”，不是主动轮询主站。主站实现见 [Modbus_zhu](https://github.com/Mingcai-ui/Modbus_zhu)。

## 1. 系统结构

```text
PC 主站（Modbus Poll / 串口助手）
        │ USART1  115200 8N1
        │ PA9=TX  PA10=RX
        ▼
┌───────────────────────────────────────────────────────┐
│ STM32F103C8T6 · 采集路由从机                          │
│                                                       │
│ frame_poll(PC) → mb_proto_check() → 地址路由          │
│                                      ├─ 0x01 → RS485  │
│                                      └─ 0x02 → 本机   │
│ DHT11(PA11) → 2s 采样 → reg_write() → 寄存器 0/1      │
└───────────────────────┬───────────────────────────────┘
                        │ USART2  9600 8N1
                        │ PA2=TX  PA3=RX  PA1=DE/RE
                        ▼
              RS485 外部变送器（0x01）
```

日志通过独立的 USART3 输出，不占用 PC 的 Modbus 二进制链路。

## 2. 已实现功能

| 能力 | 当前实现 |
|---|---|
| 双串口接收 | USART1、USART2 独立通道、缓冲、计数器和判帧状态 |
| 静默判帧 | 5ms 帧间隔，SysTick 1ms tick 驱动 |
| 缓冲保护 | 每路 255 字节，超长时冻结计数并置溢出标志 |
| 错误恢复 | ORE 等接收错误后清理本路状态并重新武装中断 |
| 帧校验 | 最短长度 4 字节，整帧 CRC16 结果必须为 0 |
| 地址路由 | `0x01` 外部透传，`0x02` 本机应答，其他地址丢弃 |
| 本机从机 | `0x02` 支持 `0x03` 读保持寄存器，其余功能码返回异常 `0x01` |
| 异常应答 | 非法数据地址返回异常 `0x02`，非法功能码返回异常 `0x01` |
| 寄存器模型 | 2 个保持寄存器，统一 `reg_read()` / `reg_write()` 并做越界保护 |
| 诊断计数 | 短帧、超长帧、CRC 错、非法地址四类计数 |
| 传感器采集 | DHT11 每约 2 秒采样一次，成功后写入本机寄存器 |
| 日志隔离 | `printf` 重定向到 USART3，避免文本日志破坏 USART1 帧流 |

## 3. 请求处理流程

1. `frame_poll()` 从 PC 通道取出一帧，并同时取得溢出标志。
2. 若接收期间发生超长，直接计入 `DIAG_FRAME_LONG`，不进入 CRC 校验。
3. `mb_proto_check()` 检查最小帧长和 CRC16；失败时分别计入短帧或 CRC 错误。
4. 按请求首字节的从机地址路由：
   - `0x01`：通过 `mb_port_send()` 原样发送到 RS485。
   - `0x02`：协议层生成应答或异常帧，再从 USART1 返回 PC。
   - 其他：计入 `DIAG_BAD_ADDR` 后丢弃。
5. RS485 通道收到外部变送器应答后，原样回传 USART1。

## 4. 地址与寄存器定义

| 地址 | 设备 | 支持范围 | 应答出口 |
|---|---|---|---|
| `0x01` | 外部 RS485 温湿度变送器 | 本机只校验并透传，不解释功能码 | USART2 → 外部设备，应答回 USART1 |
| `0x02` | 本机 DHT11 从机 | `0x03` 读保持寄存器 | USART1 |
| 其他 | 未定义 | 丢弃并计数 | 无 |

本机 `0x02` 的保持寄存器：

| 寄存器地址 | 数据 | 存储格式 | 示例 |
|---|---|---|---|
| `0x0000` | 温度 | 温度 ×10，16 位 | `275` 表示 `27.5℃` |
| `0x0001` | 湿度 | 湿度 ×10，16 位 | `590` 表示 `59.0%RH` |

DHT11 当前量程为非负温度。读取失败时寄存器保留上一次成功值，不自动清零。

| 项目 | 配置 |
|---|---|

## 7. 关键设计

### 7.1 协议层只组包，不决定出口

`mb_proto_build()`、`mb_proto_build_03()` 和 `mb_proto_exception()` 只向缓冲区写入字节并返回长度。发送端口由 `modbus_rtu.c` 的地址路由决定，后续拆分独立 router 层时不需要改协议格式代码。

### 7.2 255 字节边界与超长帧分开处理

Modbus RTU 单帧 ADU 上限为 255 字节。接收计数使用 `uint8_t`，因此缓冲写满后必须停止递增计数，只记录溢出标志；否则计数回绕会导致后续字节覆盖帧头。

### 7.3 数据模型集中管理

寄存器数组只由 `register_map.c` 持有。应用采样和协议读取都经过统一接口，越界检查集中在 `reg_write()` 等入口，避免应用层直接写数组。

### 7.4 日志与协议物理隔离

USART1 只承载 PC 的二进制 Modbus 帧，`printf` 通过 USART3 输出，避免 ASCII 日志插入协议帧导致 PC 解析失败。

### 7.5 DHT11 调度与紧贴时序读取分开

20ms 起始信号等待由状态机分步完成，不占用主循环；释放总线后的约 4ms 位级读取必须紧贴执行，并短暂关闭中断。该驱动不是完全非阻塞，这是 DHT11 微秒级时序带来的限制。

## 8. 实测记录

### 8.1 地址 `0x01` 外部透传

```text
PC → 01 03 00 01 00 01 D5 CA
PC ← 01 03 02 01 14 B9 DB
```

应答数据 `0x0114 = 276`。该记录证明请求和应答可以完整经过 USART1 → RS485 → 外部变送器 → USART2 → USART1。

### 8.2 地址 `0x02` 本机 DHT11

| 请求 | 应答 | 结果 |
|---|---|---|
| `02 03 00 00 00 02 C4 38` | `02 03 04 01 13 02 4E B8 5E` | 温度 `27.5℃`，湿度 `59.0%RH` |
| 读取越界地址 | `02 83 02 ...` | 异常码 `0x02`，非法数据地址 |
| `02 06 ...` 写请求 | `02 86 01 ...` | 异常码 `0x01`，本机当前只开放 `0x03` |

### 8.3 M3 分层回归

2026-11-19 在 v2.3.0 阶段完成以下上板回归：

| 条件 | 结果 |
|---|---|
| 关闭主循环 OLED 刷新，PC 间隔 1ms × 100 次 | 应答接收正常 |
| 短帧、超长帧、CRC 错、非法地址 | 分别拦截并计数 |
| 非法功能码 | 返回异常应答 |
| 重新开启全量 OLED 刷新 | 需要约 100ms 以上 PC 间隔才能稳定接收 |

“1ms 间隔”测试受 PC 端 USB 串口 Latency Timer 影响，线上仍可能以约 16ms 批量突发；该结果验证功能路径，不代表真实吞吐上限已达到理论值。

## 9. 构建与使用

### EIDE

使用 VS Code + EIDE 打开 `Modbus_RS485_PC.code-workspace`，选择 Debug 后编译并下载。

### 命令行

```bash
bash tools/build.sh
```

脚本使用 EIDE 自带的 `arm-none-eabi-gcc`，输出 `build/makecheck/Modbus_RS485_PC.elf`。不同机器需要同步修改脚本顶部的 `GCC` 路径。

### PC 主站设置

- USART1：115200 / 8N1。
- 外部设备请求使用地址 `0x01`。
- 本机温湿度请求使用地址 `0x02`、功能码 `0x03`、起始地址 `0x0000`、数量 `2`。
- PC 软件必须按原始二进制帧收发，不能使用 ASCII 文本模式。

## 10. 当前边界

| 项目 | 说明 |
|---|---|
| 分支状态 | `modbus_congji` 为当前采集/路由版，尚未合并默认分支 `main` |
| `0x01` 总线仲裁 | 当前没有请求—应答状态机、忙标志或请求队列；PC 高频连发可能抢占尚未结束的事务 |
| `0x02` 功能码 | 只实现 `0x03`；`0x01/0x05/0x06/0x0F/0x10` 尚未启用 |
| DHT11 冷启动 | 已取得非零实测数据，但连续上电冷启动稳定性仍需复核 |
| DHT11 采样门控 | 当前主循环无条件调用 `DHT11_Handler()`，尚未恢复“两路串口静默时才读取”的门控 |
| 长帧与吞吐 | 255 字节合法长帧和真实最高帧率尚未完成系统实测 |
| 拆包 | 不重组被 5ms 静默阈值拆开的多段请求 |
| OLED | 主循环内的全量刷新当前已注释；诊断显示代码保留，可按调试需要启用 |
| RTOS 与云链路 | 本分支仍为裸机，不包含 MQTT、离线缓存和上位机可视化 |
